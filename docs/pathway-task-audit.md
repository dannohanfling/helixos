# Success Pathway task audit

Report-only audit of the Success Pathway task library in HelixOS, read from the seed data and the code on 2026-09-15 (commit `3296b34`). Nothing in the app was changed. Sources: `src/data/seed/task_library.json`, `src/data/seed/stages.json`, `src/lib/engine/pathway.ts`, `src/lib/queries/pathway.ts`, `src/lib/queries/onboarding.ts`, `src/lib/queries/today.ts`, `src/lib/actions/pathway.ts`, `src/app/(app)/pathway/page.tsx`, `src/app/(app)/coach/page.tsx`, `src/app/(app)/coach/[clientId]/page.tsx`, `src/app/(app)/today/page.tsx`, `src/db/seed.ts`, `src/db/schema.ts`, `src/lib/webhooks.ts`, `src/components/nav-groups.ts`, plus the page files under `src/app/(app)/` for what each screen holds.

Bucket key used throughout: **1** done in the app (a screen exists and the task could link to it), **2** partly (the app touches it; the client finishes elsewhere), **3** not touched, **4** legacy or superseded (a retired tool or workflow; the old Airtable base was itself called "HelixOS" by clients).

How this reconciles with the quoted figures:

- **"215 library tasks across 7 stages"** — 215 is the number of tasks whose key is an Airtable record id (`rec…`). The other 3 (`field-big-promise`, `field-audience`, `field-revenue-goal`) were added in the app to make Stage 1 field-bound (`src/lib/engine/pathway.ts:59-68`). 215 + 3 = 218. The seed log prints `Library: 7 stages, 218 tasks` (`src/db/seed.ts:96`).
- **"58 required"** — matches. The data has 65 `must` tasks (10 / 21 / 6 / 12 / 3 / 4 / 9). Seven onboarding `must` tasks are demoted to `optional` by `ADMIN_ONBOARDING_KEYS` (`src/lib/engine/pathway.ts:14`), both at seed time (`src/db/seed.ts:43`) and again at read time through `clientFacing()` (`src/lib/engine/pathway.ts:16-18`, called from `simplePath` at line 21 and from the coach roster denominator at `src/app/(app)/coach/page.tsx:63`). 65 − 7 = 58.
- **"26 extras in Onboarding"** — matches: 29 − 3.
- **"roughly 64 in System Install"** — the real number is **59** (80 − 21). No arithmetic on the current data gives 64; the quoted figure is either from an earlier snapshot of the library or a rough count. Not determined.

Seeding rules that decide what a client actually has:

- `seedLibrary()` upserts all 7 stages and all 218 tasks by key (`src/db/seed.ts:25-48`).
- A new client gets one `pathway_progress` row per library task, status `todo`, on join (`src/lib/queries/onboarding.ts:10-16`, called from `src/lib/actions/auth.ts:84`). So every client "has" all 218, required and extra alike; the split is purely presentational.
- The simple path is one stage at a time, `must` tasks only, in `order`, at most `OPEN_LIMIT = 3` open (`src/lib/engine/pathway.ts:6, 20-48`). A stage is left only when every `must` task is `verified` (line 30). If a stage had no `must` tasks the path would fall back to `should` (line 28); this never triggers today because every stage has at least three.
- Extras are folded into a `Disclosure` under the NOW card: "Extras for this stage (n/m) · optional … Nice-to-haves. They earn points but never block the next stage." (`src/app/(app)/pathway/page.tsx:181-191`). On the whole map, anything not `must` is badged "Extra" / "· optional" (lines 65, 205).
- Future stages render read-only with "Read only until you get here." and "Unlocks when: <entryCriteria>" (`page.tsx:53-57, 71`).
- `order` collides inside stages (Onboarding orders 1–3 are used twice; System Install 207, 208 and 213 twice). JavaScript's stable sort keeps JSON order for ties, which is why the three field tasks lead Onboarding ahead of "Sign the agreement" (test at `src/lib/engine/__tests__/stage1-fields.test.ts:11-16`).
- `stages.json` `pointsAvailable` (100 / 360 / 300 / 250 / 250 / 450 / 500) does not equal the sum of task points in any stage (required-only sums are 45 / 1115 / 150 / 430 / 100 / 120 / 690; all-task sums 735 / 2920 / 540 / 810 / 360 / 750 / 1210). The field is stored but not shown on the Pathway page.

## 7. Five smaller findings

**(a) How required vs extra is decided.** Field: `priority` in `task_library.json`, one of `must` / `should` / `nice` / `optional` (`src/db/schema.ts:347`). Rule: required = `priority === "must"` (`src/lib/engine/pathway.ts:27`; the same filter at `pathway/page.tsx:106` and `coach/page.tsx:63`). Exception: the seven keys in `ADMIN_ONBOARDING_KEYS` (`engine/pathway.ts:14`: Sign the agreement; Make your first payment; Complete your onboarding form; Confirm your GoHighLevel access; Confirm your HelixOS access; Schedule your kickoff call; Request missing access and implementation assets) are rewritten to `optional` at seed (`seed.ts:43`) and at read (`clientFacing`, lines 16-18) with the comment "By the time a client is inside the app these are done or the coach's job". That is why Onboarding shows 3 required and 26 extras: the data has 10 `must` tasks there, seven are demoted, and the 16 `should` + 3 `nice` join them in the extras drawer. `should` and `nice` are never distinguished from each other anywhere in the UI; both render as "Extra".

**(b) Optimize vs System Install.** Optimize has **3** required steps (Define Ascension Path (Free → Paid → Higher Tier); Add outcome fields to key flows; Review broken automation/error logs), System Install has **21**. The three do not touch Optimize's own exit criteria ("Leak identified. One focused improvement committed. Next event scheduled. Non-buyers re-engaged. Wins captured."): the tasks that do — Identify the biggest leak; Decide what to change (one focused improvement); Refine the nurture sequence; Refine the event content or offer — are all `should`, so they sit in the extras drawer while two chatbot-builder steps and an ascension document form the required path of the week after the first event.

**(c) A visible win before Week 6?** No required step before Launch is written to produce one. Onboarding's three are fields. System Install's 21 are builds (section 7d), plus "Track purchase and conversion rate", which needs a launched campaign to have anything to track. Community's six are platform set-up, purpose, guidelines, and three chatbot webinar tasks; "First members in" is in the stage's exit criteria, but the tasks that produce it — Invite your warm audience (20–50 personal invitations), Identify people to engage with early (5–10 people) — are `should`. The first required step that names a real outcome is in Launch, Week 6: "Show up and deliver the event" and "Capture the actual numbers". The tasks whose Done-when would show a first lead or first call are all extras: Install Lead Tracking System ("at least 10 leads entered"), Track leads generated by campaign, Personal outreach to key prospects (Launch, should), and the exit criteria of System Install ("Lead capture live") say live, not "a lead". The app produces wins outside the pathway from day one — the four starter tasks ("Reach out to 3 people in your audience", `src/lib/queries/onboarding.ts:29-32`), points for DMs started, replies and calls booked (README "Points"), and the 30-day curriculum — but none of that is a pathway step.

**(d) System Install intro copy vs its steps.** Quoted exactly from `stages.json` (`description`): "This is the engine. Three phases: Lead Capture (who comes in), Nurture (how you build trust), and Conversion (how they say yes). We install your lead capture, nurture, and conversion pathway inside GoHighLevel. You show up with the raw materials — your ideal lead, your offer, your voice, your stories. We build the engine. This track runs in parallel with Community." The 21 required steps are all phrased as the client's work; none says "we" and none uses the "Work with me" wording that appears in two `should` tasks elsewhere. By kind: **5** raw-material steps (Choose where your community will live; Build internal offer brief; Map the customer journey from entry to purchase; Set your price point; Decide how buyers get onboarded), **6** GoHighLevel builds (Build registration confirmation workflow; Build registration landing page; Connect forms and buttons across funnel; Create CRM pipeline stages; Connect webinar registration to CRM and reminders; Build a Basic Email Automation Workflow with Form Trigger, Tags, Pipeline & Confirmation Email), **6** chatbot builds (Create a safe test contact process; Build comment-to-DM trigger flow; Tag and route leads by chatbot answers; Create first lead capture subflow; Route by intent; Connect entry keywords and links), **4** other builds (Install 3 Membership Questions; Install Sales Tracking Dashboard; Map All Automation Sequences; Track purchase and conversion rate). So 16 of the 21 required steps have the client building the engine the copy says "we build"; eight of them are written in the third person ("Student builds…", "Student connects…").

**(e) "Write your Big Promise": proof: checkbox and completes itself, both on one card. Confirmed.** Data: `task_library.json` first object, `"submissionType": "checkbox"` with `howTo` "Fill in the Big Promise on Settings. This task completes itself when the field is saved." Rendering: `pathway/page.tsx:220` prints `· proof: {selected.submissionType}` for every task with no exception, so the meta line reads "+15 pts · ⚡ < 15 min · proof: checkbox"; lines 265-271 then replace the form with the block "This one completes itself when the field is saved. Set it on Settings →" because the key is in `FIELD_TASKS`. Both are on the same card. A third reading of the same task on Today says "+15 pts when your coach verifies it" (`today/page.tsx:372`), for a task no coach ever sees. The schema's `submissionType` enum has no `field` value (`schema.ts:342`), which is why the data says checkbox.
